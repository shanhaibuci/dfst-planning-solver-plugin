# 求解结果解释

## 证据顺序

按以下顺序使用信息：

1. `gateway.solver_jobs.get_detail` 返回的任务状态、失败信息、公开约束摘要和安全 `engine_view`；
2. `gateway.solver_jobs.get_summary` 返回的 `result_score` 与 `result_summary`；
3. `gateway.image_versions.get_result_summary_schema` 对摘要字段的定义；
4. 当前会话中已确认的初始场景草稿；
5. 用户额外提供的脱敏业务信息。

不要调用管理员接口、场景回放接口或完整结果下载。历史任务的初始 `request_payload` 不在 MCP 能力中；缺少输入时明确说明限制。

## 输出结构

派单类成功结果在用户没有询问具体归属、拆单或原因时，默认先给业务摘要，再按证据等级补充解释。用户已询问具体问题时，先直接回答该问题，不用通用摘要、全部总体指标或完整工程师路线稀释重点。业务摘要顺序固定为：

1. **整体是否可行**：优先使用摘要 Schema 定义的明确可行性字段；没有该字段时，可以结合公开得分作带依据的合理推断；
2. **派单完成情况**：派单成功数、未派单数，以及公开结果明确给出的未派原因；
3. **总体指标**：总里程、总时间、非零吨公里费用；缺失或不适用的指标不补造；
4. **工程师派单顺序**：按公开结果列出工程师、工单顺序、可用的到达时间和服务时间；
5. **详情入口**：链接文案使用“点击查看派单路线与排程详情”。

`result_score`、`result_summary` 和结果摘要 Schema 用于判断及解释上述结论。默认不向普通用户展示原始 hard/soft score；用户明确询问算法得分时，再结合摘要 Schema 解释。任务状态为 `succeeded` 只代表求解过程成功，不能在缺少可行性证据时自动声称业务方案完全可行。

### 可确认事实

只陈述响应中直接存在的内容，例如任务状态、得分、已出现的分配关系、时间、距离、数量或失败码。

### 合理推断

说明推断依赖的字段和逻辑，并使用“可能”“与……一致”“从现有数据看”等限定语。不要说“引擎就是因为 X”或声称拿到了未提供的决策轨迹。

### 证据不足

列出缺失字段、无法验证的结论，以及用户可以补充的数据或 Gateway 查看入口。未派原因、总里程、总时间、吨公里费用或派单顺序没有公开字段支持时，明确说明缺失，不根据行业经验或其他 ImageVersion 的字段猜测。

## VRP0 分析角度

只有 `gateway.solver_jobs.get_detail` 返回的顶层 `engine_view.kind=vrp0` 时，使用以下角度：

- **硬资格**：技能、区域、工单类型、班次、时间窗、容量和必须/禁止关系；
- **时序可行性**：到达时间、服务时长、前后工单顺序、班次结束时间；
- **空间与路线**：起点、工单位置、已有路线、可能的增量距离和时间；
- **负载**：已分配数量、重量、体积、工作时长和剩余容量；
- **软目标**：总成本、距离、迟到、资源数量、均衡性等公开指标或约束摘要；
- **结果质量**：hard/soft 得分、可行性、未安排对象和异常提示。

## “为什么 A 派给 B 而不是 C”

1. 先确认结果中 A 的实际归属和 B/C 是否都出现在公开数据中。
2. 比较 B/C 的硬资格；如果 C 明确不满足，作为事实说明对应字段。
3. 两者都可能可行时，再比较时序、位置、路线增量、负载和软目标。
4. 只有字段充分时给出倾向性解释；没有引擎决策轨迹或反事实结果时，不给出唯一确定因果。
5. 如果需要严格反事实比较，说明必须创建新的对照任务。只有用户明确要求并再次完成积分提示与创建确认后才能执行。

## “为什么两单拆给不同工程师”

必须把“允许拆分的条件”与“引擎选中当前方案的原因”分开：

1. 两单没有同人关联、必须/禁止关系或其他强制关联时，只能确认“引擎被允许分开派单”；不能把关联字段为空写成本次拆分的唯一或充分原因。
2. 不得假设其他工单和工程师分配保持不变。局部移动某张工单后得到的负载分布、超班、绕路或其他变化，不是全局重新求解的必然结果；其他工单可能被重新分配和排序。
3. 只有当输入和结果明确证明所有同人方案都违反某项硬约束，或已有实际对照求解返回不可行证据时，才能说“时间窗/资格/容量迫使拆分”。只证明某一个局部改法不可行还不够。
4. 当前方案的距离、完工时间、负载数量和得分只能描述当前方案。没有“两单同人”对照方案的同口径指标时，不得声称当前方案总路程更短、总时间更少、完工更早、成本更低或负载更均衡。
5. 约束配置表示“引擎会考虑的规则/目标”，不是本次决策的归因报告。必须按三个槽位解读：`0hard/0medium/50soft` 是权重 50 的软约束，不是 Medium 约束。软约束只表示优化倾向，不能承诺必然满足。
6. 如果没有决策轨迹或对照结果，可用的默认结论是：“能确定的是当前配置允许拆分，且返回的拆分方案可行；仅凭当前结果不能确定是哪个优化目标促成了这次拆分。”此时默认不再列出“可能原因”，不做顺路性、绕路、超班或负载分布的假设性描述。约束配置中存在某个目标只能表明引擎会考虑它，不足以把它列为本次拆分的候选原因。
7. 建议分两级：“尽量同人”可使用软关联；“必须同人”必须使用 ImageVersion 明确支持的硬约束。不得用软关联向用户承诺强制同人。

推荐的简短回答顺序是：**直接结论 → 可确认事实 → 证据边界 → 可选的验证/调整方法**。对一个具体拆单问题，默认最多四个短段或四个要点，不展示通用结果概览、指标表、原始得分、全部约束清单或完整路线。普通业务回答中，使用用户给出的业务称谓区分目标工单即可，不展示内部工单 ID、`relation_tickets`、`dep_tickets`、`ref_tickets` 或约束键名；将它们翻译为“同人关联”和“前后依赖”。只有用户明确要求技术细节时才展示机器字段。未有真实对照结果时，不得在回答任何位置使用局部换单后的假设分布作为证据；同人约束下全局重新求解仍可能得到与局部推演不同的整体分配。

将“怎样调整业务规则”和“怎样验证拆分代价”分成两个不同动作，不得并称为两种强制方法。只有当前任务对应 ImageVersion 的公开能力信息明确证明某个同人硬约束可用且可覆盖时，才可给出具体机器配置值；否则只说“使用当前 ImageVersion 明确支持的硬性同人规则”。

对普通业务用户的具体拆单问题，即使结果中有约束得分，也不展示任何 `0hard/...` 数字串、约束权重或机器配置示例。这些数据不是决策归因证据，只在用户明确追问约束技术细节时解释。默认语义模板是：

1. **结论**：当前场景没有要求两单必须同人，因此引擎可以独立分配；当前拆分方案可行。
2. **事实**：两单分别派给两名工程师，且没有同人关联或前后依赖。
3. **边界**：没有决策轨迹或对照结果，不能说是时间窗、路程或负载均衡导致，也不能说拆分一定更好。
4. **下一步**：必须同人时使用 ImageVersion 明确支持的硬性同人规则；需要验证影响时建立对照任务。

不得在该模板中额外添加技术表格、得分、内部 ID、字段名、推测原因或未经确认的硬约束机器值。

## 常见状态解释

- `succeeded`：结果可用，但仍需结合摘要 Schema 解释得分和指标。
- `failed`：使用公开 `failure_code`/`failure_message`，区分输入、调度、引擎和归档阶段。
- `pending_confirmation`：平台仍在确认结果或积分收敛，不按成功或失败下结论。
- `timed_out`：任务超过平台时限；不能推断是否存在可用中间方案。
- `archive_failed`：结果归档未完成；不要绕过 Gateway 获取内部结果。

失败信息被截断、缺少字段路径或没有给出修复方式时，只说明 Tool 实际返回的内容和证据边界。除非响应明确提供了更完整信息，不得声称任务详情页、管理员页面或其他渠道可以取得完整错误，也不得猜测引擎实际接受的格式后自动重试。

结尾只给出与当前上下文真实相关的下一步：修正数据、联系管理员、稍后查询，或在明确确认后建立对照任务，并可提供 Gateway 详情入口。

回答前必须自检：是否把“允许”误写成“导致”；是否固定了其他分配后声称全局必然；是否用单一方案指标声称比另一方案更好；是否又列出未验证的可能原因、顺路性或局部换单结果；是否把 soft 槽位权重误称为 Medium；是否把软约束说成强制保证。任一项为“是”都必须改写后再输出。
